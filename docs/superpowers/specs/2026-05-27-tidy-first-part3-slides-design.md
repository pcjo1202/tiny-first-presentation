# Tidy First? PART 3 이론 — 발표 슬라이드 설계

## 개요

- **발표 주제**: 『Tidy First?』 PART 3 이론
- **관통 메시지**: "코드 정리는 결벽이 아니라 투자다. 오늘의 작은 정리가 내일의 연쇄 변경을 막는 옵션이 된다."
- **도구**: `make-slide` (npx make-slide init), Minimal Light 테마
- **발표 시간**: 20~30분
- **슬라이드 수**: 약 32장
- **스타일**: 스토리텔링 — 질문에서 답을 찾아가는 역순 구조

## 스토리 구조

"코드 정리, 먼저 해야 할까?"라는 실용적 질문으로 시작하여, 이론적 근거를 하나씩 쌓아가며 답에 도달하는 여정.

```
질문 → 가치의 두 축 → 돈의 충돌 → 판단 기준(가역성) → 비용의 정체(결합도) → 답
```

## 슬라이드 상세 설계

### Act 1. 질문 던지기 (슬라이드 1-3)

| # | 제목 | 핵심 내용 | 노트 |
|---|------|----------|------|
| 1 | 코드 정리, 먼저 해야 할까? | 타이틀. 부제: 『Tidy First?』 PART 3 이론 | 심플하게 질문만 |
| 2 | 여러분은 코드를 언제 정리하나요? | 기능 구현 전? 후? 안 함? 청중 참여 유도 | 잠깐 손 들어보기 가능 |
| 3 | PART 3이 던지는 네 가지 질문 | 1) 설계란? 2) 비용과 설계의 관계 3) 구조 투자의 장단점 4) 판단 원칙 | "오늘 이 질문들에 답을 찾아갑니다" |

### Act 2. 소프트웨어의 가치는 어디서 오는가 (슬라이드 4-9)

| # | 제목 | 핵심 내용 | 노트 |
|---|------|----------|------|
| 4 | 소프트웨어 설계 = ? | "요소들을 **유익하게** 관계 맺는 일" | 한 문장 정의, 큰 글씨 |
| 5 | 세 가지 키워드 | 요소(Elements), 관계(Relationships), 유익하게(Beneficially) 표 | 각각 소프트웨어 예시 포함 |
| 6 | Box.area() 예제 | Before: caller가 width*height 직접 계산 / After: box.area() 호출 | 코드 스니펫 Before/After |
| 7 | 가치의 두 축: 동작 vs 구조 | 가시성·평가·사람들의 반응 비교 표 | "구조는 보이지 않지만 미래를 만든다" |
| 8 | 기계 비유 | 1번(1→10) vs 2번("될 수 있는" 기계). 어느 쪽에 더 돈을 내겠는가? | 청중에게 질문 던지기 |
| 9 | 선택 가능성을 앗아가는 세 가지 | 핵심 직원 퇴사, 고객과의 거리, **변경 비용 상승** ← 대응 가능 | 3번에 강조 |

### Act 3. 돈의 두 얼굴이 충돌한다 (슬라이드 10-15)

| # | 제목 | 핵심 내용 | 노트 |
|---|------|----------|------|
| 10 | 돈의 두 본성 | 시간 가치 vs 옵션 가치 — 양쪽 대비 레이아웃 | 두 컬럼 |
| 11 | 시간 가치 | "오늘의 1달러 > 내일의 1달러". 사용 불가, 투자 불가, 불이행 위험 | 3가지 이유 리스트 |
| 12 | 시간 가치의 결론 | → 코드 정리는 **나중에**! 먼저 벌고, 나중에 쓰자 | 단, 정리+변경 < 바로 변경이면 먼저 |
| 13 | 옵션 가치 | 감자 콜 옵션 비유. 동작 변경=감자, 설계=프리미엄 | 비유를 시각적으로 |
| 14 | 옵션에서 배운 4가지 교훈 | 질문 자체의 가치, 목록 확대, 예측 불필요, 불확실성의 역설 | 번호 매겨서 |
| 15 | 충돌! | "나중에!" vs "먼저!" — 시간 가치와 옵션이 줄다리기 | 전환점. 긴장감 |

### Act 4. 판단의 기술 (슬라이드 16-20)

| # | 제목 | 핵심 내용 | 노트 |
|---|------|----------|------|
| 16 | 줄다리기 | 현금흐름할인 → 나중에 / 옵션 → 먼저. 표로 대비 | |
| 17 | 확실한 경우 | 비용(정리+변경) < 비용(바로 변경) → 무조건 먼저 정리 | 수식 강조 |
| 18 | 곤란한 경우 | 비용 분산, 옵션 가치 우위, 자기 관리 — 3가지 논거 | |
| 19 | 가역성 — 핵심 판단 기준 | 머리(되돌림 가능)=가볍게 vs 문신(영구)=면밀히 | 비유를 시각적으로 |
| 20 | 되돌릴 수 없는 변경 다루기 | 서비스 추출→feature flag / integer→long→한 번에 하나씩 | "되돌릴 수 있게 만들기" |

### Act 5. 비용의 정체를 밝히다 (슬라이드 21-27)

| # | 제목 | 핵심 내용 | 노트 |
|---|------|----------|------|
| 21 | 결합도란 | coupled(E1,E2,Δ) ≡ ΔE1⇒ΔE2. "어떤 변경에 대해" 명시 필요 | 수식 + 설명 |
| 22 | 결합도가 악몽인 이유 | 일대다(1:N) + 연쇄작용 → 멱법칙 분포 | 소수의 큰 변경 = 전체 비용 대부분 |
| 23 | 페이스북 사례 | 같은 랙, 다른 팀, 백업 변경 → 장애. 서로의 존재도 모름 | 실제 사례로 임팩트 |
| 24 | 콘스탄틴의 등가성 | Step 1→2→3. 비용(SW) ≈ 변경 ≈ 큰 변경 ≈ 결합도 | 3단계를 순차적으로 |
| 25 | 통신 프로토콜 예제 | Before(직접 결합) → After(포맷 도입). 결합도 감소 but 완전 제거 아님 | 코드 스니펫 |
| 26 | 핵심 통찰 | "한 종류의 결합도↓ → 다른 종류↑". 모든 결합을 없앨 수 없다 | 가장 중요한 통찰 강조 |
| 27 | 응집도 | 결합된 요소를 한곳에. 스카우트 규칙: "찾았을 때보다 나은 상태로" | |

### Act 6. 답을 찾다 (슬라이드 28-32)

| # | 제목 | 핵심 내용 | 노트 |
|---|------|----------|------|
| 28 | 네 가지 힘 | 비용, 수익, 결합도, 응집도 — 정리 판단 프레임워크 | 표 |
| 29 | 가장 중요한 변수: 여러분 | 최상의 상태에서 주체적으로 일할 때 더 나은 프로그래머 | 감성적 마무리 |
| 30 | 프링글스 주의! | 코드 정리 = 소프트웨어 설계의 프링글스. 만족하기 쉬워 억제 필요 | 유머 포인트 |
| 31 | 결론 | "코드 정리는 결벽이 아니라 투자다" + 시리즈 로드맵(나→동료→조직) | 관통 메시지 반복 |
| 32 | 토론거리 | 4가지 질문 제시 → 토론 시작 | 마지막 장으로 토론 유도 |

## 기술 사양

- **도구**: `npx make-slide init` → Minimal Light 테마 선택
- **출력**: 단일 HTML 파일
- **코드 스니펫**: JavaScript 사용 (노션 원문과 동일)
- **레이아웃**: 텍스트 최소화, 키워드와 비유 중심
